# RAG

## 1.RAG vs 微调

|      | RAG                                 | 微调                               |
| ---- | ----------------------------------- | -------------------------------- |
| 成本   | 初始成本低（主要成本是知识库构建），无需训练模型，运行时需要检索资源。 | 初始成本高（训练+调优），但推理成本低              |
| 维护难度 | 知识更新简单，只需要更新知识库                     | 知识更新困难，需要重新微调模型                  |
| 响应速度 | 检索+生成，速度受检索影响，可能稍慢                  | 直接生成，延迟低                         |
| 准确性  | 依赖检索质量，能减少幻觉                        | 对训练数据质量敏感，有过拟合风险                 |
| 适用场景 | 多领域问答、企业知识库、动态知识场景等知识更新频频古较高的场景     | 固定领域任务、特定风格生成、低延迟应用等知识更新聘频率较低的场景 |

从上面的表格感觉好像是在放大RAG的优势，然后弱化微调的价值。其实上它们两个都是不可替代的。

**RAG解决的是“模型不知道”，而微调解决的是“模型不会”**。RAG更适合个人开发者。对于没有团队、没有算力、没有标注体系的我们来说，RAG是最现实的路线了。

## 2.RAG评价指标

RAG场景下，比较著名的评估模型方法的框架是：RAGAS。RAGAS方法在评估过程中主要使用忠诚度，答案相关性和上下文相关性来评判整个RAG系统中LLM生成的答案的质量。RAGAS方法的一个优点是不需要参考答案。

具体来讲，**忠实度**是指用户判断LLM的输出是否是根据召回文本的内容生成的。

**答案相关性**是衡量生成的答案是否和用户的答案相关的。

**上下文相关性**是用于判断召回文本是否和用户问题相关的。

具体来讲：

**忠实度**的计算方式通常包括两个步骤：

1.使用LLM生成的问题和答案，让大模型生成多个陈述。

2.让LLM**判断**是否可以通过召回的文本，推断出这些陈述。最后$\frac{采用能够推断出来的陈述}{总陈述量}$作为忠诚度的评分。

**答案相关性**：根据LLM的回答生成若干个假问题，然后计算假问题和真问题的相似度，将相似度平均值作为答案相关性的评分。

**上下文相关性**：让LLM挑选出召回文本片段中能够回答用户问题的文本子集，用文本子集占召回文本的比例作为上下文的相关性数值。



在RAG的工作流程当中，**整个RAG过程如下：**

用户提问——>问题经过Embedding模型——>问题向量——>在向量数据库当中通过相似度计算得到——>N个最相似片段——>N个最相似片段和问题向量经过cross-encoder模型——>得到M个最相似片段——>M个最相似片段对应的文本和问题文本发送个大模型——>大模型做出解答



在这个过程中，**问题向量——>在向量数据库当中通过相似度计算得到——>N个最相似片段——>N个最相似片段和问题向量经过cross-encoder模型——>得到M个最相似片段** 这段过程被称为召回+重排。召回+重排这个过程当中会有一个考察的指标，即找出来的文档、文本、片段是不是对的。**召回+重排**对应的指标是**上下文相关性**。主要考察，在向量数据库当中通过相似度计算和重排得到的M个文本，和用户的问题相关吗？它评估的是**召回的质量**。



**大模型做出解答** ，即大模型给出的解答，是否是在回答用户问的问题，是否是跑题的。**答案相关性**它评估的是大模型生成的质量，回答是否是紧扣用户问题的，而不是输出一堆正确但是没有关系的废话的。大模型的输入有两部分，一部分是用户问题，一部分是检索出来的文本。这个衡量的是大模型有没有关注到用户提出的问题。



**大模型做出解答**，即大模型给出的解答，能否从召回+重排的文本中推出。是否存在大模型自说自话的问题，或者幻觉问题。**忠实度**它评估的是回答是不是有证据支持，而不是在凭空编造。大模型的输入有两部分，一部分是用户问题，一部分是检索出来的文本。这个衡量的是大模型有没有关注到检索出来的文本。



**忠实度为什么要拆成“陈述——>验证”这两步呢？**

问题$Q$ 

上下文$C$

回答$A$

如果我们要判断$A$是否忠实于$C$。这是一个高度整体、模糊和不可分解的判断任务。

如果让模型进行整体判断的话，**一个答案往往包含多个事实点**，你不能只做整体判断，否则会出现：  “整体看起来对，但里面夹了一条胡编”。

所以必须把**整体判断**变成**可验证的原子命题**

核心的设计动机是：把一个不可判定的整体问题，转换为多个可判定的局部问题。把复杂系统，拆成可验证单元。

所以忠实度要分成两步走。Step1 答案变成原子事实。Step2 逐条判断是否可以由上下文推理出。

这里面是经典的NLP框架，信息抽取(IE)、自然语言蕴含（NLI）。

信息抽取是指：从非结构化文本中自动提取出结构化、明确的关键信息。

自然语言蕴含判断的是：一个文本是否能逻辑上推出另一个文本。





**“答案相关性”为啥要用“生成假问题再比相似度”？**

核心直觉：如果回答真的在回答用户的问题，那么：从这个回答反推出来的”它在回答什么问题“，应该是和原问题很接近的。

它的好处是：

- 不直接让 LLM 给分（减少主观）

- 更像“语义对齐度”衡量

它的局限是：

- 如果答案很泛（模板化废话），也可能生成出很接近的“泛问题”，导致分数虚高

- 相似度模型/embedding 的选择会强烈影响结果

**泛的本质不是语义不对，而是信息密度为零。**

**如果满足以下 3 条中的 2 条，基本就是“泛答案”：**

1. 去掉领域名词仍成立

2. 没有任何可核验事实

3. 可以回答 10 个不同问题



泛化的回答举例，例如：**提升效率和用户体验是构建现代智能系统的重要目标**，这句话可以适用于所有的AI问题。





**”上下文相关性“为啥用”可用片段占比“**

上下文相关性本质上要衡量的是：召回回来的上下文里面，有多少是”能用来回答问题的证据“，有多少是噪声。

目前的做法是
1.让LLM在召回的文本当中挑出”能回答问题“的片段子集。

2.用”子集占全部召回文本的比例“作为分数。

但是值得注意的一点是：”比例天然偏好短文本“。比例指标惩罚“长上下文”，而不是“差上下文”。模型会学到：**尽量少给上下文，而不是给对上下文。**



Chunk 指的是：把原始长文本切分后得到的、作为检索与建模基本单位的文本片段。

Chunk 是向量检索的基本单位，是在“语义完整性”和“检索精度”之间取平衡的工程切分结果。

当前方法是在拼接后的上下文中基于文本片段长度计算相关性，本质上属于 token 级评估；而 chunk 级评估则以检索单元为最小粒度，对每个 chunk 独立判断其是否相关，再统计命中比例，从而避免因 chunk 长度差异带来的比例偏置。

我明白了，这里的所有chunk都是1。只要我这个chunk当中有就行，不用在乎这个当中有用的是多少。这有些类似于token归一化，这两个本质上是一样的。



举个例子：

- chunk1：100 token，其中 10 token 有效

- chunk2：100 token，其中 20 token 有效 

如果是用token来进行计算的话：

总 token = 100 + 100 = 200      有效 token = 10 + 20 = 30        所以：30/200=0.15

上下文相关性 = **0.15**

chunk 级通常不是看“有多少 token 有效”，而是：每个 chunk 只要包含有效信息，就算是 1。

chunk1：有有效 token → 相关    chunk2：有有效 token → 相关    相关 chunk 数 = 2总 chunk 数 = 2/2=1.0    上下文相关性 = **1.0**
