###### 1.Agent的记忆功能

核心：Agent记忆不是“模型永久记住了一切”，而是一套把过去信息保存、筛选、检索并在需要时重新放入上下文的机制。

1. 为什么上下文窗口不能直接承担全部长期记忆？
   1. 使用的是RAG式的长期记忆。首先长期记忆可能内容很多，可能会超过上下文窗口的token容量。其次，长期记忆也不是所有记忆都和当前对话和问题相关，如果全部放进去，和当前内容相关的长期记忆反而被稀释了，没有突出重点。
2. 短期记忆和长期记忆最根本的区别是什么？
   1. 短期记忆通常存在于上下文窗口，包含最近的对话信息，智能体回复，工具调用结果，以及当前交互的反思内容。
   2. 长期记忆是智能体在各种交互场景、任务执行过程中需要长时间保存的信息。
   3. 最大的区别是会话结束后，短期记忆会丢失，但是长期记忆是保存在智能体运行环境之外的，不会因为对话结束而丢失，也可以跨对话存在。
3. “用户刚把预算从 5000 改成 3000”属于哪种记忆？“用户长期偏好中文回答”又属于哪种？
   1. 第一个处于短期记忆
   2. 第二个属于长期记忆

短期记忆在逻辑上服务于当前会话或任务；它可以被持久化用于故障恢复，但不会像长期记忆一样默认跨会话检索和复用

###### 2. 上下文压缩

- 为什么只保留最近几轮原始消息，Agent 仍可能做错？
  - 对话很长时，需要进行上下文压缩，但是不能只保留最近几轮的原始信息。因为早期可能包含任务目标、用户已经确认的约束、关键决定或者工具结果。如果把这些内容给丢掉的话，Agent后面就可能重复提问、做错方向或违反约束。
- 压缩历史时，哪些信息必须保留？
  - 任务目标、已经确认的约束、关键决策、重要的工具结果、未完成的事项
- 如果摘要漏掉了关键约束，可能产生什么后果？
  - Agent可能会重复提问、做错方向或者违反约束等。漏掉关键约束还可能造成前后回答不一致，或执行带来成本、安全风险

###### 3.长期记忆

长期记忆是存放在上下文窗口之外、可跨会话复用的信息。

关键在于：选择值得长期保存的信息->写入外部存储->当前任务需要时检索相关内容->放回模型上下文

- 为什么不能把每一段历史对话都直接写进长期记忆？
  - 如果每段历史对话都放入长期记忆，一个是存储需求会大大增加。另一个就是筛选需要的长期记忆是很难精准定位了。类似于RAG任务，当文档过多时，每次定位成本高，而且准确率会有所下降。
- 哪类信息适合写入长期记忆？
  - 用户稳定偏好
  - 跨会话仍然成立的事实
  - 可复用的历史经验
  - 程序性知识
  - 仍在持续推进的长期任务关键信息
- 长期记忆最终是怎样帮助模型回答当前问题的？
  - 在存储的所有长期记忆中，检索当前任务相关的内容，然后把这部分长期记忆放入到模型上下文当中

长期记忆的三种常见内容类型：语义记忆、情景记忆、程序性记忆。

区别：

- 语义记忆：保存相对稳定的事实、概念和用户偏好

- 情景记忆：保存过去某次对话、任务或事件的经历及结果

- 程序性记忆：保存“如何做事”的方法、步骤和工作流，不只是某次成功案例。

Agent coding场景中：
语义记忆：用户偏好中文；项目使用 Python；

情景记忆：上次修复某个 Bug 时，尝试过哪些方案，最终哪种方案有效。

程序性记忆：遇到 Bug 时，先复现问题，再读日志、定位模块、修改代码、运行测试、最后记录结果。

###### 4.LangChain 中的记忆功能实现

在 LangChain 这类框架里，为什么短期记忆和长期记忆最终都仍然要“回到模型上下文”才能发挥作用？

模型这次推理时只能看到本次请求传入的上下文。短期记忆即使暂存在会话状态里、长期记忆即使存在数据库或向量库里，它们若不被重新放入模型输入，模型就“看不见”，自然无法利用。

- **短期记忆**：维护当前会话的消息历史。新一轮提问到来时，把近期对话或压缩摘要一起放进 Prompt，让模型知道“我们刚才聊到哪里、当前任务做到哪一步”。

- **长期记忆**：把可跨会话复用的信息保存到外部存储中。新任务到来时，用当前问题检索相关内容，得到少量相关记录，再注入 Prompt。检索器在实现上就是“输入查询，返回相关文档/记录”的组件。

###### 5.LangGraph 中的记忆功能实现

| 类型   | LangGraph概念        | 作用范围                 | 核心用途                |
| ---- | ------------------ | -------------------- | ------------------- |
| 短期记忆 | State+Checkpointer | 当前thread_id对应的会话或者任务 | 保存对话、工具结果、任务进度和中间状态 |
| 长期记忆 | Store+namespace    | 跨thread_id、跨会话       | 保存用户偏好、可复用事实、经验和流程  |

state:是当前Agent执行过程中的状态容器。它不只是放聊天信息，还可以放任务目标、已确认约束、工具调用结果、当前步骤等。

checkpointer:负责把这个state按执行步骤保存为检查点。每次agent调用模型或完成一次工具调用后，状态都可以更新并持久化。

thread_id：当前会话或任务的唯一标识，把不同会话的state间隔开。

LangGraph把短期记忆定义为单个thread内的状态，并通过checkpointer持久化，状态会在每一步开始时读取，结束后更新。

store:独立于某次会话状态的外部存储。它通常按 namespace 组织

namespace: namespace是Store 中用于**组织、分区和定位长期记忆的逻辑命名空间**，可理解为一组分层分类键。

###### 6.长期记忆的常见应用场景

| 场景             | 适合保存什么            | 长期记忆带来的作用            |
| -------------- | ----------------- | -------------------- |
| 对话式 AI / 聊天机器人 | 用户偏好、历史摘要、关键话题    | 不用让用户重复自我介绍，对话更连贯    |
| 个性化服务 AI       | 用户偏好、历史行为、画像信息    | 调整推荐和服务策略，更贴合用户      |
| 智能客服 / 售后 AI   | 历史工单、问题处理记录、满意度反馈 | 快速了解历史问题，避免重复排查或重复询问 |

长期记忆只保存跨会话有复用价值、仍可靠且允许保存的信息；使用时按当前任务检索少量相关内容，不应把全部历史直接塞回上下文。
