### 1.1常见的Agent开发框架

###### AutoGPT

自主型Agent框架，通过”思考-执行-反思-再规划“循环自动推进任务，强调高自主性与多步任务拆解能力，但可控度较弱。

###### LangGraph

基于有向图的Agent流程框架，用状态机+图结构确保任务步骤可控、可观测、可解释，适合多步工作流的稳定执行。

###### Dify

面向应用构建的LLM平台，提供UI化的工作流，工具集成与模型管理，降低Agent/AI应用开发门槛，强调易用性和产品化。

###### CrewAI

多Agent协作框架，让多个具备角色与技能的Agent自主协作完成任务，适合开放式探索和需要团队分工的复杂任务。

###### AutoGen

微软开源的多Agent协作框架，强调”人机协作+多Agent对话控制“，具备较强的可调试性、可观测性与对话流控制能力。

### 1.2LangChain核心设计理念和框架

Langchain的核心思想是通过模块化组件，**Prompt、Memory、Tool、Chain将LLM与外部数据源，工具（向量数据库，多种LLM）结合**，形成**可复用的”链式逻辑“**。特点是灵活，生态丰富，适合快速原型开发。

###### 1.2.2 LangChain 1.0新版本

LangChain v1.0的升级标志着LangChain已经走出”实验阶段“，称为一个稳定的、可用于生产的框架。在这次升级中，引入了以下新特性：

1.智能体的全新创建方式

- 之前的Agent创建方式复杂，需要手动配置多个组件，

- v1.0提供更简介的API，通过标准化的构建流程，开发者可以快速定义Agent的行为、工具调用逻辑，并且支持更复杂的任务编排

2.中间件机制

- 类似Web框架的中间件概念，可以在执行链路中插入逻辑

- 应用场景：日志记录、性能监控、错误重试、缓存、权限控制

- 好处：开发者无需修改核心逻辑，就能在执行过程中添加这些功能，提升可维护性。

3.结构化输出

- 之前LLM输出是纯文本，容易出现格式错误

- v1.0支持JSON 文件和Pydantic类型验证，可以强制模型输出符合预期结构

- 好处：减少LLM不确定性，适合生产环境，尤其是需要严格数据格式的场景。

4.标准内容块

- 提供标准化的Prompt模板、工具接口、链组件

- 好处：降低重复开发，开发者可以直接复用官方标准块，减少定制成本。

5.全新包结构与模块化设计

- 命名空间重构：拆分为langchain_core（核心逻辑）、langchain_community（社区集成）、langchain_experimental(实验功能)

- 好处：模块职责更加清晰，升级和维护更方便，避免以前版本中”包太大、依赖混乱“的问题。

###### 1.2.3 LangChain不方便的地方

###### 1.依赖过多，复杂度高

LangChain集成了大量向量数据库，模型提供商和工具。理论上可选，但是实际应用中很多功能需要安装大量的依赖，导致项目臃肿，出现”依赖地狱“。对于简单项目来说，很麻烦和没有必要。

###### 2.频繁更新，接口不稳定

迭代更新速度太快，API接口经常变化，需要不断重构代码，维护成本太高。

###### 3.性能和延迟问题

LangChain链式调用每一步都可能涉及外部API，导致延迟明显，尤其是需要实时响应的场景表现不佳，链式调用也增加了出错概率和调试难度。

###### 4.不够灵活，定制困难

高度抽象导致很多底层逻辑无法轻易改变。

###### 1.3 LangGraph

###### 1.3.1 LangGraph介绍/主要模块

LangGraph通过将任务组织为有向图，而不是线性链，来解决LangChain在复杂任务中的局限。它支持**条件分支、循环、并行执行和状态共享**，并且能够实现多Agent协作和复杂工作流。

核心模块包括：

- Graph：整体工作流的图结构

- Node：图中的计算单元

- State：共享状态，用于节点间传递上下文

- Edge：连接节点，定义控制流和数据流

###### 1.3.2 LangGraph过程是如何流转的？

**定义图结构**：用StateGraph 添加节点和边，指定入口节点（*set_entry_point*()）和结束条件（*END*）。

**编译图**：调用*graphcompile()*,生成一个可执行图对象（相当于执行器，复杂调度和状态管理。）

**启动执行**：通过*invoke（initial_state）* 或 *stream(initial_state)* 开始运行，传入初始状态。

**执行逻辑** ：

- 从入口节点开始执行。

- 根据边决定下一个节点，如果多个节点同时满足条件，就并行执行。

- 每个节点跑完后，把输出合并到共享状态。

- 重复调度，直到路由到*END* 或没有后续节点。

结束：返回最终状态，或者用*stream（）* 观察每一步的状态变化。

**疑问：LLM在哪里呢？在哪个步骤起作用呢？**

LangGraph 本质上是一个基于状态机的 Agent 工作流框架，它负责节点调度、状态管理和流程控制。LLM 本身并不在 StateGraph 或 compile 阶段运行，而通常封装在具体节点内部。当 invoke() 启动图执行后，流程从入口节点开始运行。如果某个节点内部调用了 llm.invoke()，此时才真正向 GPT、Qwen、DeepSeek 等模型发送请求并获取结果。

节点执行完成后，会把结果写回共享状态，LangGraph 根据边和路由规则决定下一步执行哪个节点，直到到达 END。因此 LangGraph 负责流程编排，而 LLM 负责推理生成，两者是协作关系而不是同一个东西。

**疑问：** LangGraph需要提前定义节点（Node）和边（Edge），并构建完整的图结构后才能执行。那么这与传统的Workflow的固定流程模式有什么本质的区别呢？Agent 通常被认为适用于开放式、非固定流程的问题，而 Workflow 更适用于可预先定义流程的场景。在这种情况下，LangGraph 是如何体现 Agent 的自主决策能力的？

**答案**：LangGraph 和 Workflow 的区别，不在于有没有图（Graph）、有没有节点（Node），而在于“谁拥有决策权”。LangGraph 预定义的是“能力空间（Capability Space）”，而不是“执行路径（Execution Path）”。Workflow 的执行路径是程序员提前确定的。Agent 的执行路径是在运行过程中由 LLM 根据当前状态动态决定的。LangGraph 恰恰是为了让这种动态决策、循环反思、工具调用和状态管理变得可控而设计的。

**Agent 不是 Workflow 的对立面。Agent 通常运行在 Workflow 提供的框架之内**
