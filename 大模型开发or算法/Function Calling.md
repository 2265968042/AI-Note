Function Calling 不是模型真的“执行函数”，而是让模型把自然语言意图转换成一个结构化的调用建议。

完整链路：

工具定义和Schema-->模型选择工具并生成name+arguments-->Harness解析、校验、执行-->工具返回真实结果或错误-->Observation回填给模型-->模型决定下一步

Function Calling：解决“模型如何提出一次工具调用”

ReAct：解决“模型如何基于Observation多轮决定下一步”

MCP：解决Host如何统一连接、发现和调用外部能力

**为什么模型生成了合法 JSON，也不能直接执行工具？**

模型只负责生成结构化请求，模型生成的调用是不可信的输入，需要进行校验。

模型负责选择下一步和生成参数。Harness负责：

- 判断调用格式是否正确

- 限制可访问的文件、命令和权限

- 运行真实工具

- 把日志作为Observation回填

- 遇到重复失败时限制重试、触发重规划或停止

**Server/Tool**：执行最终的资源、权限和业务校验，不能只信任 Harness 或模型。



**调用失败如何定位和修复**

| 失败类型       | 典型表现                  | 如何处理                                 |
| ---------- | --------------------- | ------------------------------------ |
| 该调用却没有调用   | 模型直接编答案，没有查文件或者运行测试   | 补充工具描述、示例和“何时必须调用工具”的测试样本            |
| 不该调用却调用    | 已有信息足够，仍重复查同一内容       | 加入“不调用工具”的负样本，Harness检测无进展循环         |
| 选错工具       | 想读文件却调用搜索；想跑测试却调用修改代码 | 工具职责单一、命名清晰、描述明确，减少功能重叠              |
| 参数格式或值错误   | 漏必填字段、类型不对、文件路径错误     | inputSchema 约束类型/必填项/枚举/范围；返回具体可修正错误 |
| 工具执行失败     | 超时、网络错误、权限不足、资源不存在    | 区分临时故障、业务错误、权限错误、修正或停止               |
| 工具成功但目标未完成 | 测试命令执行成功，但测试仍失败       | ReAct 的规划与目标验收问题                     |
