### 1.Agent幻觉

幻觉的本质是：模型生成了看似合理、但没有可靠性证据支持的内容、行动或结论。

| 类型    | 例子                                  |
| ----- | ----------------------------------- |
| 事实幻觉  | 没查资料，就编造了某个API、文件内容或项目规则            |
| 上下文幻觉 | 已经拿到日志，却忽略日志内容，得出不受证据支持的结论          |
| 工具幻觉  | 编造不存在的工具、参数、文件路径，或者假装工具执行成功         |
| 状态幻觉  | 测试没有通过，却认为BUG已经修复了。任务没有完成，却认为已经完成了。 |

模型的目标是生成**在当前上下文最像合理答案**的后续token，不天然具备事实验证器。

幻觉通常来自：

- 当前上下文缺少完成任务所需的真实信息

- RAG召回内容缺失、过时、冲突或噪声太多

- Tool描述不清，模型误选工具或编造参数

- Prompt强迫模型“必须给出答案”，却没有允许它说不确定

- 工具调用失败后，模型没有正确利用Observation

- 上下文过长，关键约束、日志或工具结果被淹没

- 系统只检查最终自然语言，没有验证真实产物和执行状态



请不要编造”可以放进 Prompt，但只是软约束，不能构成可靠保障。

通过Prompt约束，并不能真正约束幻觉。要通过Harness来进行约束

结论/动作——>必须有证据——>证据来自检索文本、工具结果、代码变更或测试日志——>Harness/Server验证证据与状态——>满足任务验收条件

### 2.如何降低幻觉

核心：不是寻找一个不会幻觉的模型，而是让每一层都不完全信任模型，并用下一层校验上一层。

###### 2.1模型行为层

目标：让模型在不确定时少猜少编

- 选择指令遵循、工具调用和结构化输出能力更稳定的模型

- 在系统指令中明确：没有证据时说明不确定。不假设工具成功。不编造文件、API、测试结果

###### 2.2上下文与RAG层

目标：给模型提供足够、相关、可信且不过量的依据。

RAG能减少“模型不知道还硬答”的幻觉，但不能保证召回内容本身正确。

###### 2.3工具层

目标：让模型从真实环境获取事实，而不是凭空猜测。

例如 Mewcode 要判断测试是否通过，不能靠模型说“应该修好了”，而要调用Tool来进行检查。Tool设计要清晰，Schema要严格、错误信息要可修正。工具返回的exit code、测试报告、文件内容和实际diff，是比模型自述更高等级的证据。

真实执行结果/测试报告>文件、数据库、版本化文档>RAG召回文本>模型自身的自然语言判断

###### 2.4Harness层

目标：把“模型认为完成”变成“系统验证完成”

Harness要做的包括：

- 校验工具调用、参数、权限和风险

- 保存任务目标、约束、工具结果和进展状态

- 发现重复调用、无进展循环和异常重试

- 设置步数、时间、token、费用预算

- 对高风险动作要求用户确认

- 设置最终验收条件

Harness依据这些外部状态决定任务是否成功。

###### 2.5评测与监控层

目标：持续发现系统仍会在哪些地方产生幻觉。

离线阶段要准备：

- 模型不知道答案、必须拒答的样本。
- RAG 召回不足、冲突或过时的样本。
- 不该调用工具、工具不存在、参数诱导错误的样本。
- 工具返回失败后，模型是否会假装成功的样本。
- 测试未通过但模型宣布完成的样本。

上线后通过 logs、traces、metrics 和用户反馈，找出新幻觉案例；再回流评测集，避免同类问题再次出现。
