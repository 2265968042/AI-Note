### 1.MCP本地Server和远端Server

核心：MCP Server在哪里运行，就决定了能力离谁更近、谁负责资源和安全、以及能否被多人共享。

- 本地和远端 MCP Server 最根本的区别是什么？
  - 一个部署在本地机器，一个部署在云端或者远程服务器。Server的运行位置不同，因此带来资源访问范围、通信方式、延迟、权限治理和共享能力的不同。
- “读取你电脑上的项目文件”和“全公司查询统一设备知识库”，各选哪一种？为什么？
  - 读取电脑上的项目文件选择部署在本地Server
  - 全公司查询统一设备知识库选择云端Server
- 为什么远端 Server 更适合团队共享？
  - 可以集中实现认证、授权、审计等安全机制。
  - 不影响本地app性能，在远程完成
  - 多人共享，不依赖于某个人的机器

### 2. MCP的传输协议

MCP Client和Server传递的不是自然语言，而是JSON-RPC消息。标准传输方式主要是STDIO和Streamable HTTP。

- 为什么本地 MCP 更适合 STDIO？
  - 本地MCP Server，通常部署和运行在本地机器上，可以直接通过本地接口或者STDIO(标准I/O)进行通信。不必经过网络、HTTP、认证和长连接管理，结构更简单、延迟也更低。
- 为什么不能再简单回答“远端 MCP 一定使用 SSE”？
  - 旧版远端 MCP 使用 HTTP+SSE 传输；在 2025 年 3 月后，推荐的传输方式改为 Streamable HTTP。它以 HTTP `POST` 和 `GET` 为基础，Server 可以直接返回 JSON，也可以按需使用 SSE 流。因此 SSE 不再是远端 MCP 的必选传输方式。
  - 无论是否使用 SSE，Streamable HTTP 都基于 GET 和 POST；SSE 是其中一种可选的流式响应与服务端通知方式。
- SSE 在 Streamable HTTP 中现在承担什么作用？
  - SSE 是可选增强能力，适合流式返回多个消息、实时进度通知或 Server 主动向 Client 发送通知。普通请求可以直接返回 JSON，不必建立 SSE 流。

### 3. MCP Server Tool

MCP Tool的设计目标是：让模型能选对工具、传对参数、读懂结果，并在失败时安全地修正。

MCP Tool 是 MCP Server 对外暴露的“可调用能力”；它通常由一个函数实现，但底层也可以是一次 API 请求、数据库查询或一个业务流程。

- **入参**：输入到 MCP Tool 的参数格式，也就是 `arguments`。
- **出参**：MCP Tool 执行后的返回格式，也就是 `structuredContent`、`content` 等结果。
- **不是直接指用户输入或模型最终自然语言输出**，而是指一次 Tool 调用两端的数据契约。

六个方面：入参设计、出参设计、错误处理、Tool Annotations、工具粒度、安全与校验。

###### 1.入参设计

- 为什么说 `inputSchema` 是“给模型看的接口说明书”？
  - LLM是根据inputSchema来构造Function Call的参数的
- 为什么参数不能设计得越多越灵活越好？
  - 关键是要传递参数的准确性。参数应当最少化，但必须足以完成任务。tool 入参应遵循最小必要原则：必填参数尽量少，类型清晰，能默认的给默认值，有限选项使用枚举，数值加范围约束。这样既降低模型传参的不确定性，也方便 Server 校验和拒绝非法请求。
- 默认值、枚举和数值范围，分别怎样减少模型传参错误？
  - 默认值、枚举选型和数值范围，都是为了让模型的选择更加少。当选择更少的时候，准确率更高。：**缩小合法输入空间，并让 Server 能明确校验非法输入。** 举例，目标检测中是与不是的01检测要远远比多目标检测简单。

###### 2.出参设计

MCP Server Tool的输出结果，最好同时满足：

程序 / Client：需要稳定、可校验的结构化数据
模型 / 人：需要容易理解和利用的内容

举个outputSchema的格式：

```
{
  "type": "object",
  "properties": {
    "documents": { "...这里是 documents 的规则..." }
  },
  "required": ["documents"]
}
```

解释：

outputSchema：定义整个 Tool 返回对象的结构。
其中规定：返回对象必须包含 documents 字段；（required部分体现）
documents 是一个文档列表，列表中每个文档再包含 title、source、score 等字段。

- 为什么 Tool 结果不能只给一段自然语言？
  - 要机器也能看懂，最好结构化输出。不是因为模型看不懂自然语言，而是因为 Client、下游程序和校验逻辑需要稳定、可解析的数据；只靠自然语言解析会很脆弱。
- `outputSchema` 和 `structuredContent` 分别是什么？
  - outputSchema：定义整个 Tool 返回对象的结构。
  - structuredContent：按照 outputSchema 返回的真实机器可读数据。

###### 3.错误处理

错误处理本质：让系统知道这次失败是“请求格式根本不对”，还是“工具收到了合法请求但执行没成功”。

协议级错误：`tools/call` 请求本身不符合 MCP / JSON-RPC 规则

Tool执行错误：请求格式正确，Tool 已开始执行，但业务失败

- 为什么“可用集合是 A、B、C”比 Python 堆栈更好的错误信息？
  
  - 因为它能据此改参数后重试。MCP 规范也明确区分协议错误与 `isError: true` 的执行错误，并建议把可修正的执行错误提供给模型

- “查询结果为空”一定算错误吗？为什么？
  
  - 查询结果为空不一定是错误，也许结果本身就没有找到，这个时候应该返回空，而不是返回不相干的信息，干扰模型。只有请求无法执行时才应标记 `isError: true`

###### 4.Tool Annotations

不是工具的业务参数，也不改变Tool的执行逻辑，而是Server给Client的一组行为和风险提示。常见的：

- readOnlyHint：是否只读，不修改环境

- destructiveHint：是否可能造成破坏性修改

- idempotentHint：相同参数重复调用，是否不会产生额外影响

- openWorldHint：是否会接触开放的外部世界

Tool Annotations 是对 Tool 行为和风险的元数据声明，帮助 Client 做确认、展示、重试和安全策略决策；但它们只是提示，不能替代真实的权限校验。

- `readOnlyHint` 与 `destructiveHint` 的区别是什么？
  - 前者是只读，不修改环境。后者是判断是否会造成破坏性修改。
- 为什么知识库查询 Tool 应标记为 `readOnlyHint: true`？
  - 知识库查询是召回相关的内容，并不是改变知识库
- 为什么 Annotations 不能替代 Server 的权限校验？
  - Annotations 只是 Server 声明的风险提示，可能配置错误，也可能来自不可信 Server；它们不能真正阻止越权访问。Server 必须在执行 Tool 前做真实的身份认证、权限校验和业务校验。

###### 5.工具粒度控制

原则：一个Tool尽量是只负责一件清晰的事情，但多个Tool能够自然组合完成复杂任务。

- 为什么 Tool 太粗会让模型更容易出错？
  - 同时承担多个操作，模型难以理解，参数也会更多，安全风险也会更加复杂/
- 为什么 Tool 太细会让 Agent 的调用链更不稳定？
  - Tool 设计应遵循单一职责和可组合原则。工具过粗会混合多种职责，导致参数复杂、模型难选、风险难控；工具过细会拉长调用链，增加调用失败、延迟和成本。合理粒度应让上一步输出能够自然作为下一步输入。
- “列出集合 → 查看集合详情 → 查询知识库”为什么是较合理的拆分？
  - 模型可以先发现有哪些集合，再了解集合内容，最后查询知识库。

###### 6.安全与校验

核心原则：inputSchema合法，不等于业务上安全合法。Server必须把所有输入当作不可信数据，再做真实校验。

Server 侧至少应做：

- 输入校验：类型、范围、路径、注入风险、业务规则。
- 权限控制：当前用户是否有权访问该集合或执行该操作。
- 限流：避免被频繁调用导致资源耗尽。
- 输出清洗：脱敏 PII、过滤不应回传的内部信息。

高风险操作，例如删除资料、发送邮件、修改生产数据，还应由 Host 要求用户确认，即保留 human-in-the-loop。

- 为什么 `inputSchema` 合法，Server 仍不能直接执行 Tool？
  - inputSchema合法，不等于业务上安全合法
- 为什么权限校验必须由 Server 执行，不能只信任 Host 或 Client？
  - 权限校验必须在 Server 端执行，因为 Server 才是实际资源和业务操作的控制点。Host、Client 或模型的请求都可能配置错误、被篡改或被绕过；只有 Server 端校验才能真正阻止未授权访问。
- 高风险操作为什么仍需要用户确认？
  - 高风险操作可能造成不可逆后果，如删除数据、发送消息或修改生产配置。用户确认能保留最终控制权，避免模型误判、提示注入或参数错误直接造成损失。

好的 MCP Tool 要做到：入参少而明确、出参结构化且可读、错误可修正、风险有标注、粒度可组合、安全由 Server 兜底。
