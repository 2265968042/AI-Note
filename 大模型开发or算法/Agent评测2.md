### 1.Agent评估全景图

Agent 评测不是只看最终答案，而是沿着生命周期评估：开发前定标准，开发中测组件，上线前测完整链路，上线后看真实反馈。

- 开发前：
  
  - 定义成功标准。比如任务完成率、工具调用准确率、回答质量、延迟、成本和安全边界等等
  
  - 模型选型。比较不同模型在目标场景下的效果、成本、延迟和稳定性等

- 开发中：
  
  - 对agent的关键组件分别进行测评。包括 Prompt、RAG 检索质量、工具选择、参数生成、规划能力、多轮对话状态管理等。
  
  - 同时观察中间轨迹是否合理，比如是否选对工具、参数是否正确、是否能根据工具结果继续规划

- 上线前：
  
  - 做端到端测评。验证完整任务链路是否稳定完成。
  
  - 进行小规模用户测试、仿真测试、安全测试等，并建立自动化评测pipeline

- 上线后：
  
  - 基于真实流量持续监控，包括任务成功率、失败率、工具调用错误率等等。
  
  - 发现问题后回流到测试集和评测 pipeline 中，持续迭代。

### 2.评测细节

###### 2.1 LLM-as-a-judge

- `LLM-as-a-judge` 是什么？
  - 是一个（通常更强的）大模型，按照预先写好的评分标准`rubric`，去给另一个Agent的输出打分或排序。它是目前最主流的自动评估手段。
- 为什么 Agent 评测需要它？
  - Agent的输出大多是开放式自然语言，没有唯一的标准答案，没有办法像传统评测那样进行精确匹配。LLM能像人一样理解语义，又能像程序一样批量自动化跑。
- 它有哪三种典型用法？
  - 单点打分：给一个输出打一个绝对分
  - 对参考打分：把输出和“标准答案”相比，判断是否一致，进行打分。
  - 两两比较：给出A、B两个输出，让裁判选择哪个更好。
- 它有什么缺点或风险？
  - 自我偏好：裁判偏向自己生成的答案。
  - 首位偏差：两两比较时偏向排在前面的那个。
  - 冗长偏差：偏向更长的回答，哪怕没更好。

看不到裁判模型和它的提示词，就不要相信它给的分数。

不同 judge 模型、prompt、rubric 的分数不可直接横向比较

###### 2.2 比较式评估

**是什么：** 不给某个结果打绝对分数，而是针对同一个问题，将不同的Agent或者模型的输出两两比较，由人或LLM Judge 选出更好的一个；收集大量胜负结果后，进一步形成模型排名。

**为什么测：** 很多开放式回答很难准确打绝对分数，但比较两个答案哪个更好通常更容易，更加稳定。所以适合评估和排序多个Agent或模型

**怎么测：** 

针对同一批问题，分别生成多个Agent回答

让人工评委或者LLM Judge对两个回答进行投票

最后根据胜负记录，用 Elo 或 Bradley-Terry 等方法计算整体排名。

**和 A/B 测试有什么区别：** 

A/B 测试通常是线上的：将不同版本分给不同用户群，比较真实业务指标，例如留存、转化、满意度和投诉率。

比较式评估通常是离线的：同一个问题的多个输出交给同一个评委比较。

**风险是什么：** 

偏好不等于正确。评委可能更喜欢语气讨好、篇幅更长但实际错误的回答。
因此需要专业评委，并注意首位偏差、冗长偏差等问题。

**补充：**

有些任务能用程序直接判断对错，就不要优先让大模型当裁判。比如让 Agent 写 SQL：SQL 能否执行、结果是否正确，可以直接验证；这比让另一个 LLM 主观打分更客观、更便宜，也更容易复现。

1.功能正确性：有标准答案，或能实际执行验证。

2.相似度。有参考答案，但允许措辞不同，例如翻译、摘要。

3.困惑度。衡量模型对文本的“意外程度”，可辅助判断语言流畅性或发现测试数据污染；

能用功能正确性就不用相似度，能用相似度就不优先用LLM as a judge

越靠前就越客观、便宜和可复现。

### 3.选型期：选基模

选模型不是“榜单第一就选谁”，而是“业务场景需要什么能力，就选能满足这些能力、成本和约束的模型”，最后再用私有测试集进行验证。

场景->能力需求->候选模型->私有测试验证->最终选择

- 为什么不能只按模型排行榜选基模？
  - 公开榜单可能存在数据污染，导致排名虚高
  - 榜单任务和我们的任务未必相关
  - 闭源模型涉及成本和数据隐私
- 选基模时，除了回答质量，还要考虑哪些因素？
  - 硬性约束：成本上限、延迟上限、是否支持私有部署、上下文长度
  - 软指标：回答质量和能力
  - 是否贴合应用场景
  - 是要自建开源模型还是要调用API
  - 最终必须用真实业务数据构建私有测试集验证。
- 如果 Agent 必须调用外部工具，模型最关键的能力是什么？
  - function calling能力，包括能否选对工具、稳定生成正确参数，同时还需要稳定的结构化输出和指令遵循能力。

**如何用“硬约束先筛选、软指标再比较、私有测试集最终验证”的方式完成选型。**

```
第一步：硬约束筛掉不合格模型（成本、延迟、私有化部署、上下文长度和工具调用支持）
第二步：从剩余模型里挑几个候选
第三步：用自己的真实任务测试，选最合适的（比较任务成功率、工具调用准确率、成本和延迟）
```
