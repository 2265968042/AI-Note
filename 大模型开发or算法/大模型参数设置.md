### 1.大模型参数设置

核心：参数是在控制模型生成时的随机性、候选范围、输出预算和重复倾向；设置必须服务于任务目标，并通过评测验证。

| 参数类别 | 代表参数                               | 本质上控制什么              |
| ---- | ---------------------------------- | -------------------- |
| 随机性  | temperature                        | 模型选token时敢不敢偏离最高概率答案 |
| 候选范围 | top_p                              | 每次生成时允许从多大的高概率候选集合里选 |
| 输出预算 | max_tokens/max_output_tokens       | 最多允许模型生成多长的内容        |
| 重复倾向 | presence_penalty\frequency_penalty | 是否鼓励新内容、抑制重复表达       |

- `temperature` 和 `top_p` 分别控制什么？
  - temperature：改变整体概率分布的陡峭程度。低温时更倾向最高概率token，结果更稳定；高温时低概率token更有机会被选中，结果更多样。
  - top_p，只保留累计概率达到P的那批候选token，再从中采样。P小，候选范围更窄，P大，候选范围更广。
  - `temperature` 控制“随机程度”，`top_p` 控制“可选范围”。
- 为什么 `max_tokens` 不能只设得越大越好？
  - max_tokens是输出长度的硬上限，主要用来控制成本、响应时间、输出是否过长、跑题、Agent是否产生过度冗长的中间内容。
  - 设得过小可能导致 JSON、工具参数或最终答案被截断；设得过大则可能增加成本，或让模型输出不必要内容。

确定任务目标
-> 选择一个保守基线配置
-> 用真实 evalset 测成功率、格式正确率、成本和延迟
-> 每次只改变一个关键参数
-> 保留更符合目标的配置

- `presence_penalty`：倾向减少已经出现过的内容，鼓励引入新概念或新话题。

- `frequency_penalty`：倾向减少高频重复的词或表达。

- 为什么 Mewcode 这类 Agent 通常应采用偏低随机性的配置？
  
  - Mewcode 以稳定执行、工具调用准确率和结构化输出为目标，通常从偏低随机性的配置开始，减少无意义的执行路径波动；但低随机性不等于一定正确，仍需通过 Schema 校验、工具结果验证和 evalset 来保证可靠性。

### 2.A2A

核心：A2A解决的是“一个Agent怎样把任务交给另一个独立Agent”。

A2A，Agent-to-Agent，是让不同团队、框架、厂商或者运行环境中的Agent能够发现彼此、委派任务、跟踪进度并获取结果的互操作协议。

- A2A的三个关键对象：
  
  - Agent Card:发现对方能做什么、怎么调用、如何认证。相当于 Agent 的“服务说明书”，描述身份、能力、技能、服务地址和认证要求。
  
  - Message：发起或补充任务。调用方发给目标 Agent 的请求。
  
  - Task：跟踪一个可能耗时很长的任务。目标 Agent 处理任务后的状态载体。它可以是处理中、已完成、失败、取消等，并可返回结果产物或进度更新。

- 说明 A2A 和 MCP 的区别
  
  - MCP 让 Agent 使用外部能力；A2A 让 Agent 协作外部 Agent。

| 对比      | MCP                       | A2A                    |
| ------- | ------------------------- | ---------------------- |
| 连接对象    | LLM 应用 / Agent 与工具、资源、提示词 | 一个 Agent 与另一个 Agent    |
| 调用目标    | 通常是函数、数据库、文件、API 等能力      | 具备自主规划和执行能力的外部 Agent   |
| 调用方关心什么 | 工具名、参数、返回结果               | 对方能力、任务状态、最终交付         |
| 典型用途    | “帮我查设备手册”                 | “请外部维修调度 Agent 处理维修安排” |

- 举一个 Mewcode 中可能使用 A2A 的场景：
  
  - Mewcode 自己负责理解需求、修改代码、运行测试。但在提交前，需要经过一个由安全团队独立维护、独立部署的“代码安全审计 Agent”检查。
  
  - Mewcode
    -> 发现安全审计 Agent 的 Agent Card
    -> 发送审计任务：代码 diff、仓库信息、审计范围
    -> 得到一个异步 Task
    -> 安全审计 Agent 用自己的模型、规则和扫描工具完成检查
    -> 返回漏洞结论、证据和修复建议
    -> Mewcode 根据结果修复或请求人工确认

如果所有子 Agent 都在同一个系统、同一个 Orchestrator 内部，并且只是内部 Tool Call 或 Handoff，未必需要 A2A。
