### 1.Agent架构

核心：多Agent不是“把一个Agent拆成好几个”就会更强。它只有在以下收益大于代价时才值得引入：**专业分工/并行处理/独立验证的收益>通信、协调、上下文同步、错误处理、成本和延迟的代价。**

要首先判断：单Agent或固定工作流能否完成？不能时，具体卡在并行、专业分工、验证还是动态探索哪个场景了。

**五种架构**

| 架构     | 如何协作                     | 适合什么情况               | 主要代价                 |
| ------ | ------------------------ | -------------------- | -------------------- |
| 单Agent | 一个Agent顺序调用工具、规划和执行      | 强顺序依赖、工具密集、任务较清晰     | 长链中一步错误可能影响后续        |
| 独立并行   | 多个Agent各自完成同一任务、最后投票或汇总  | 多方案生成、并行评审、独立样本处理    | 结果可能重复或共同犯错，聚合不一定能纠错 |
| 中心化    | Orchestrator拆任务、分派、验收、汇总 | 任务可拆分，但需统一口径、质量控制    | 中心Agent可能成为瓶颈        |
| 去中心化   | 多个Agent点对点交流、协商和纠错       | 动态探索、路径不唯一、需要多视角互动   | 通信量大，状态容易膨胀和失控       |
| 混合式    | 中心化管控+有限的Agent间直连        | 大型复杂任务，既要全局收敛又需要局部协作 | 设计与治理成本最高            |

架构越自由、Agent间通信越多，探索能力可能更强，但成本、延迟和错误传播风险也越高。

**强顺序任务**：优先单 Agent 或固定工作流。

**可独立并行的子问题，但需统一结果**：选中心化。

**路径不唯一、信息不断变化、需要互相发现和纠错**：可考虑去中心化。

**只是想多生成几个候选答案**：独立并行即可。

先以单Agent为基线，只有任务确实能从分工、并行或独立验证获益时，才引入多Agent，并根据任务依赖、统一性要求和探索不确定性选择合适拓扑。



### 2.Agent的通信和状态管理

核心：核心不是Agent之间怎么进行聊天，而是谁拥有控制权、谁能看到哪些状态、传递哪些信息、失败后由谁处理。

**三种通信模式**

| 模式            | 控制权                 | 适合场景                 | 直观理解                  |
| ------------- | ------------------- | -------------------- | --------------------- |
| Handoff（移交）   | 转给下一个Agent，原Agent退出 | 用户意图或任务阶段已经明确切换      | 接力跑，把执行权和必要上下文交出去     |
| Tool Call（委派） | 主Agent保留控制权         | 主管需要调用专家Agent完成明确子任务 | 把子Agent当成一个有输入输出契约的工具 |
| 消息协作          | 多个Agent长期驻留、互相发消息   | 持续协作、横向通信、并行推进       | 多人协作群，各自接收、处理和发布消息    |

**Handoff例子**

客服 Agent 判断用户需要预约维修，将用户身份、设备信息、问题描述交给预约 Agent；之后由预约 Agent 继续对话并完成预约。

**Tool Call 例子**

主管 Agent 调用“日志分析 Agent”，传入设备编号和时间范围；日志 Agent 返回结构化分析结果。主管仍保留最终决策权，决定是否继续查手册、创建工单或向用户追问。

**消息协作例子**

多个网页搜索 Agent 持续发布“已发现的来源”“待验证结论”“新搜索线索”；其他 Agent 可以订阅、认领或补充任务。它适合动态探索，但治理难度最高。



**状态共享**

并不是所有消息都要共享，默认原则是：私有过程尽量私有，跨Agent只共享完成协作所需的最小、结构化、可验证信息。

- 共享完整过程：把中间推理、工具调用、执行轨迹都写入共享状态。
  
  - 好处：其他Agent了解前因后果，便于协作和排查
  
  - 代价：上下文快速膨胀、Token成本变高，可能暴露不该共享的信息

- 只共享最终结果或结构化摘要：子Agent在私有状态中完成工作，只返回必要结论、证据、置信度和下一步建议。
  
  - 好处：边界清晰、成本更低、状态可控。
  
  - 代价：其他Agent看不到全部过程，必要时难以追溯。

**怎样避免协作失控**

多Agent系统至少应明确：

- 每个Agent的职责和边界，避免重复劳动

- 输入输出Schema，避免自然语言传递造成歧义

- 共享状态由谁写、谁读、谁负责最终版本

- 任务ID、状态、超时、重试次数和停止条件

- 子Agent结论冲突时，谁按照什么证据裁决

- 局 Token、时间和费用预算

- 每次调用和消息传递的 trace，方便定位“错在谁、错在哪一步”。



**Handoff 本身不一定必须做成多 Agent。**

如果同一个 Agent 既能判断维修需求，也能调用预约工具、继续完成对话，那么它就是单 Agent，只是内部换了任务阶段。

所以关键不在于“任务有没有换阶段”，而在于：后续工作是否交给一个具有独立角色、上下文、工具或权限边界的 Agent，并由它接管控制权。



### 3.架构设计题的通用解法

任务目标与约束->是否真的需要多Agent->选择架构->划分职责->设计通信与状态->设计验收、异常和停止机制->补齐安全、成本、延迟与可观测性

###### 1.明确目标与约束

先说清楚系统最终要交付什么，以及什么不能违反。例如：用户创建行程后，系统要识别时间、地点和偏好冲突，并给出可执行的改期建议；约束是不能修改用户行程、建议必须符合时间窗口、响应时间不能过长。

###### 2.判断是否需要多Agent

先以单 Agent 或固定工作流为基线。只有任务存在可独立的专业分工、可并行的子任务、独立验证需求，或动态探索路径时，才引入多 Agent。否则协调成本可能高于收益。

###### 3.选择架构

大多数业务设计题，回答**中心化 Orchestrator + 专业子 Agent**最稳，因为职责、权限、验收和最终输出都容易控制。

###### 4.划分Agent职责

每个 Agent 都应有清晰的输入、输出、工具和权限，避免“每个 Agent 都什么都能干”。

###### 5.设计依赖、通信与状态

- 输入输出采用结构化 Schema。
- 子 Agent 默认只返回必要结论、证据、置信度和下一步建议。
- 共享任务状态要有唯一责任方，通常由 Orchestrator 维护。
- 使用 `task_id` 关联同一次任务，并记录状态，如 `pending / running / completed / failed`。

###### 6.验收、异常与停止

不能把“所有 Agent 都执行完了”当成任务完成。

要明确：

- 子任务是否完成的验收规则；
- 最终方案是否满足用户约束；
- 工具失败时有限重试、降级或人工兜底；
- 子 Agent 结论冲突时由谁按什么证据裁决；
- 满足目标或超出预算时如何停止。

###### 7.补齐工程治理

按最小权限给每个 Agent 分配工具和数据访问范围；设置全局 Token、时间和费用预算；记录任务 trace、Agent 输入输出、工具调用和失败原因，并与单 Agent 基线比较成功率、成本和延迟，验证多 Agent 是否真的有收益。



**核心：先用单 Agent 或工作流解决；只有拆分带来明确收益时才引入多 Agent；能做成 Tool 的能力，不轻易做成独立 Agent。**
