# RAG重要步骤

### 1.切割

###### 1.1切割策略

| 切割策略    | 简介                                                                | 优点                   | 缺点                      |
| ------- | ----------------------------------------------------------------- | -------------------- | ----------------------- |
| 固定长度切割  | 按固定token或字符数切割，如每段512个token                                       | 实现简单，适用于结构均匀文本       | 可能打断语义，影响上下文理解          |
| 按段落切割   | 以自然段落为单位进行切割                                                      | 保持语义完整，适合结构清晰文档      | 段落长度不一，chunk大小不均匀       |
| 滑动窗口切割  | 使用滑动窗口技术，chunk之间有重叠，一般重叠的文本长度占整个文本的10%-20%                        | 保留上下文，减少语义断裂         | 增加计算和存储成本，信息冗余          |
| 语义切割    | 根据语义边界或词汇分布进行智能切割。比如使用NLTK（一种分析自然语言文本的python库，以及一些基于深度学习的模型来进行切分） | 语义完整性强，适合复杂文本        | 实现复杂，依赖额外工具或模型          |
| 结构化切割   | 根据标题、子标题、列表等文档结构进行切割                                              | 适合技术文档、报告等结构化内容      | 对结构要求高，非结构化文本效果差        |
| 递归字符分块器 | 核心思想是：按照优先级递归使用分割符进行切分，尽量保持语义完整性，而不是简单粗暴地按照固定长度截断。                | 语义保留好，灵活性高，适用于多种文本结构 | 仍然可能打断语义，不理解语义边界，块大小不均衡 |

###### 1.2 如何避免语义被切掉

滑动窗口方法中，切割的相邻两块之间都会有一些重叠。按照语义切割的方法，天然也会想语义表达一个意思的块来切割到一个chunk中。这些方法会缓解语义被切掉的问题。同时也可以使用一些对切割后的结构进行评估的方法，比如使用模型来判断语义是否完整等方法来进行评估，对语义丢失严重的切块重新分割。



###### 1.3为什么需要切割

1.大语言模型的限制。LLM有最大上下文窗口限制，直接输入整篇文档可能会超出限制。通过切割后的文本输入到LLM中可以控制上下文大小，确保模型能够正常处理并生成准确回答。

2.嵌入模型的限制。嵌入模型存在两方面的问题：一是输入长度限制（如bge-base-zh-V1.5的token限制），超出时会被截断导致语义信息丢失；二是即使不截断，文档过长也会稀释关键信息，使得embedding向量无法有效表示核心语义，影响检索精度和相关性。

###### 1.4如何确定切块的大小？

核心原则：chunk size的选择不是拍脑袋，而是一个有方法论的工程决策。

###### Step1：确定计量单位—字符还是token？

| 计算方式  | length_function | chunk_size=1000含义 | 中英文对等？     |
| ----- | --------------- | ----------------- | ---------- |
| 字符    | len             | 1000 Unicode字符    | 中文信息量远大于英文 |
| token | tiktoken.encode | 1000 token        | 基本对等       |

- 用字符计：中文1000字符大概1500到2000 token，英文1000字符大概200-250 token

- 用token计：中英文在同一个数字下信息量对等
  
  如果系统需要处理中英文混合文档，强烈建议按token计量
  
  

###### Step2:确定embedding模型的最佳输入区间

embedding模型有max_token上限，但最佳区间远小于上限：

- text-embedding-ada-002:max 8191token，最佳100-800token

- text-embedding-3-small/large:max 8191token，最佳100-800token

- BGE/Sentence-Transformers：max通常是512token，最佳100-400token

chunk的token数应该落在模型的最佳区间内，太短信息密度不够，太长语义被稀释了。

###### Step3：看文档的自然语义粒度

不同类型的文档，自然段落/语义单元的大小不同：

- FAQ/知识条目：自然语义单元100-300字—>chunk 300-500字/200-400token。

- 会议纪要/SOP：自然语义单元200-400字—>chunk400-600字/400-600token。

- 技术文档/报告：自然语义单元300-600字—>chunk600-800字/500-800token。

- 法规/合同/论文：自然语义单元500-1000字—>chunk800-1200字/700—1000token。
  
  **理想状体：一个chunk刚好包含一个完整的语义单元，不多不少。**
  
  ###### Step4：考虑下游LLM的窗口预算
  
  假设LLM窗口128Ktoken，拼prompt后可用context约8k-16ktoken
  
  - 召回top-10个chunk：每个chunk不超过800-1600token
  
  - 召回top-5个chunk：每个chunk可以到1600-3200token
    
    一般top-k=5到10，所以单个chun控制在500-1000token是安全区间。

###### Step5：设定overlap

overlap是相邻两个chunk之间”重复保留“的内容。Overlap指的是相邻chunk之间重复保留的文本区域，用于避免语义在chunk边界处被截断，从而提升embedding表达质量和RAG检索效果。

经验法则：overlap=chunk_size的10%到20%

- 太小（<10%）:边界信息丢失风险高

- 太大（>30%）：冗余存储和计算浪费，相邻chunk高度重复

- 常见配置：chunk_size=500字符+overlap=100字符，或者chunk_size=800字符+overlap=150字符

###### Step6：实验验证

上面步骤给出的都是经验区间，最终值需要实验来确定：

1.准备一个golden test set（20-50条真实查询+标注的正确答案来源）（标准测试集）

2.分别用3-4个chunk_size(如400/600/800/1000)跑一遍完整pipeline（整个处理流程）

3.对比hit_rate（命中率）(正确答案是否在top-k中)和MRR(正确答案排第几)

4.选指标最好的那个值。

RAG 并不会把整个文档直接输入 LLM，而是先将长文档切分为多个 chunk，对每个 chunk 做 embedding 并建立向量索引。在用户查询时，系统只检索与问题最相关的 top-k chunks，再将这些相关上下文输入 LLM 进行生成了。

所以chunk_size=min(embedding的最佳区间上限，LLM窗口预算/top_K)。

这个是综合考虑的，既要考虑embedding步骤的事情，又要考虑LLM步骤的事情。

### 2.召回

###### 2.1 召回的常用策略

RAG系统可以使用粗排+重排两个阶段来完成召回。粗排通常使用稠密检索模型来做语义匹配，召回语义相关文档。当然也可以再结合稀疏向量检索模型来补充使用，因为稀疏向量检索模型更擅长捕捉关键信息来提高召回效果。

粗排后，可以使用交叉编码器，比如BERT来对候选文档进行深入语义排序，提高召回质量。

###### 2.2稠密向量和稀疏向量

RAG系统中的文本向量检索模型大致分成两类：一类的基于BERT，GPT等深度学习模型的稠密向量检索模型，另一类是以TF-IDF，BM25为代表的稀疏向量检索模型。稠密向量检索模型更擅长提取文本中语义信息，稀疏向量检索模型更擅长提取关键信息。

###### 2.3 对称检索和非对称检索

对称检索是找到相似的句子，与向量检索基于计算向量相似度的原理天然匹配，只需要模型具有较强的内容抽象的能力即可。

非对称搜索是根据问题召回答案，要求模型能够将问题和答案映射到同一空间，而问题和答案通常具有不同的文本结构。并非所有的向量化模型都支持非对称检索，只有经过大量问答数据的模型才能够提供支持。

### 3.召回优化策略

###### 3.1短文本全局信息增强

因为切块的过程中难免会造成全局文本信息的丢失，因此我们为切块后的短文补充其所属的长文本信息。我们可以将长文本的前三句话，长文本的标题，长文本的关键词作为全局信息，和切块后的文本一起保存。

###### 3.2召回内容上下文扩充

在RAG切块的时候，对长文本切块后，可能会有较大的信息损失，因为我们从数据库中召回的通常是短文本。这时我们可以采用召回内容上下文补充的方法：召回的是短文本，但是输入LLM处理的是短文本的父文本（长文本）。好处是既精准（基于短文本匹配）又完整（基于长文本输入）。

在Langchain中，我们可以使用ParentDocumentRetriever来完成这一功能，它使用了两个分割器，Parent_splitter和child_splitter。前者用于确定在RAG场景下输入到大模型的父文本块的大小，后者确定从向量数据库中召回的子文本块的大小。同时还会存储父子文本块的映射关系。当使用get_relevant_documents召回时，返回的实际上是父文本的内容。

###### 3.3 文本多向量表示

在构建向量数据库的时候，可以使用多种向量来表示同一段文本。比如有一段文本A，我们不仅可以使用完整的A来生成向量，还可以使用它的子集，总结句来生成补充向量。当召集任意的补充向量对应的文本后，并不是将其输入大模型中，而是将其对应的文本A输入。

常见的生成补充向量的方法有：

文本切块：将原始文本切块后保存到数据库中，可以在召回时增强对更细粒度的表示。

文章摘要：利用LLM生成摘要。

假设性回答：可以利用大模型的能力，根据文本提出问题，把问题作为补充信息。这种方法的思想是用问题召回问题比用问题召回答案更容易。

###### 3.4内容查询优化

很多情况下，用户提出的内容有口语化，语义模糊和无关内容多等问题。因此直接将问题变成向量可能和用户的真实意图不相关，从而影响RAG场景下的召回效果。因此可以对用户的原始问题进行改写和扩充，再进行召回。

常见的对原始问题优化的方法有：

1.用LLM改写和扩充，比如LangChain提供的MultiQueryRetriever就集成了这个功能。

2.对历史问题进行总结，然后再进行召回，这个特别适用于多轮对话当中。

###### 3.5召回文本重排序

在RAG场景下，默认使用的是向量召回，检索效率高。但是由于文本向量化的过程中存在着信息损失，并且在召回过程无法考虑查询用户和候选文本上下文关系，因此召回精度不高。所以召回向量后，通常还会进行召回文本的重排序的精选。

最常用的重排序的模型是基于Transformer编码器架构的交叉编码器。将用户查询和一段候选文本同时输入到模型当中，预测它们之间的相关性分布。

###### 3.6 结合元数据召回

在实在实际场景中，很多情况我们不需要在整个向量数据库中进行召回。如果在存储文本向量的时候同时记录了每个向量相关的标签，就可以在召回时根据标签信息过滤出所需要的向量子集，有利于提高检索速率，避免检索无用的信息。
