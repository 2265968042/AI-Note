###### 1.Skill

本质：Skill是一份可复用的“任务操作手册包”，它告诉Agent在什么场景下该采用什么流程、读哪些资料、调用哪些工具、遵循哪些约束，以及如何验收结果。

Skill不是模型训练，也不是一个新模型。被加载后，Skill的指令和必要资料最终仍会进入模型上下文，影响模型此刻如何完成任务。

###### 2.Skill的作用

Skill本质就是Prompt。Skill的核心内容通常是Prompt，但 Skill 不等于一段 Prompt。它是“任务说明 + 触发条件 + 参考资料 + 脚本/模板 + 加载机制”的可复用任务包。

只有一个总的Prompt时，所有任务规则堆在一起：模型既要处理代码修复，又要处理发布、数据分析、文档写作。Prompt会越来越长，规则也容易互相干扰。

Skill 的做法是把领域经验拆成按需加载的模块：

用户任务——>判断是否匹配某个Skill——>加载该Skill的工作流程与约束——>按流程调用工具、读取资料、完成任务——>验证结果

###### 3.Skill的典型结构

```
skills/
  database-migration/
    SKILL.md          # 触发条件、流程、约束、验收标准
    references/       # 领域规则、资料、示例
    scripts/          # 可重复执行的确定性脚本
    templates/        # 报告、配置或代码模板
```

- SKILL.md是给模型看的任务说明书

- references/是需要时再读的详细知识

- scripts/和templates/是可复用资产，不只是文字提示

核心是渐进式加载：先只让模型看到每个Skill的名称和简短描述；任务匹配后再加载SKILL.md；确实需要才读取参考资料或者运行脚本。这样能减少上下文占用和规则干扰。



Skill不能靠自己保证模型一定遵守，它本质还是上下文指导，模型指令并非绝对强制执行；真正的权限、参数校验、高风险确认和停止条件，仍应由Harness、Server和工具侧控制。



###### 4.如何设计一个好Skill

Skill的目标不是把所有知识都塞进去，而是让Agent在正确场景下，以低成本、低歧义地完成一类任务。

###### 4.1何时触发

每个Skill都需要清楚说明适用范围和不适用范围。否则多个Skill都像万能助手，模型很难选对。

###### 4.2输入和前置条件是什么

要明确任务开始前必须具备什么信息。

这一步的本质是减少模型猜测。信息不够时，应要求澄清或停止，而不是自行补全。

###### 4.3流程如何写

流程应按关键决策点组织，而不是写成长篇泛泛说明。

每一步都应明确：使用什么工具、成功标准是什么、失败后怎么办。

###### 4.4哪些内容按需加载

- SKILL.md：任务范围、主流程、安全边界、验收标准

- references： MySQL特有语法、公司迁移规范、故障案例

- scripts: schema检查、迁移验证、回滚检查

核心规则常驻、细节资料按需读取，确定性动作交给脚本。

**“核心规则常驻”** 更严谨地说是：**Skill 被选中并加载后，核心规则应始终保留在该任务的上下文中。**

###### 4.5如何验收

Skill 不能只写“完成后告诉用户”。它要说明什么外部证据能证明完成。模型说“已完成”不算完成；真实工具结果和验收条件满足，才算完成。



###### 5.Skill、Prompt、RAG、MCP的边界与组合

| 需求           | 模块       |
| ------------ | -------- |
| 当前任务的总体需求    | Prompt   |
| 这类任务的成熟做法    | Skill    |
| 本次任务所需的真实事实  | RAG      |
| 查询或操作外部系统的能力 | MCP/Tool |

Skill 不负责证明事实，也不负责强制权限；它负责把“模型临场发挥”变成“尽量遵循成熟流程”。RAG 提供证据，MCP/Tool 获取或改变外部状态，Harness 负责把整个过程控制住



###### 6.Skill的测试与治理

Skill本质上会改变模型的行为，因此不能只靠“我读起来觉得流程写的不错”。它也会发生回归：改了流程、参考资料或描述后，模型可能不再触发它，或者按错步骤执行。

一个Skill至少测四件事：

- 触发正确性：该用Skill时能否选中

- 排除正确性：不该用时能否不加载，不该使用该 Skill 时，系统不应错误加载它；必要时应选择其他合适的 Skill，或不加载任何 Skill。

- 流程正确性：是否按关键步骤调用正确工具。

- 结果与安全：是否完成任务、满足约束、没有越权



测试集要包含反例和边界例。

- 正例：明确匹配Skill任务

- 负例:明显不应触发的任务

- 边界：表达模糊、同时匹配多个Skill的任务

- 失败：工具报错、前置条件缺失、用户未确认高风险操作



Skill要有版本。

Skill改了描述、流程、脚本或参考资料，就可能改变Agent行为，因此应该记录版本。

这样出了问题才能追溯，是模型变了、工具变了、还是某个Skill版本导致的。



权限不写在Skill里“相信模型遵守”，真正的强控制应该在Harness、Server或者工具权限层。

Skill 要像代码一样治理：有触发与排除测试、有边界和失败样本、有版本和 trace 可追溯，安全权限由 Harness/Server 强制执行，线上失败持续回流评测集。





**主问题：什么是Skill？你会如何设计和治理它？**

Skill是面向一类任务的可复用操作手册包。它包含使用场景、任务流程、约束、参考资料、脚本或模板以及验收流程。它不是模型训练，也不等于一段普通Prompt；但被加载后，其中的指令和必要资料会进入模型上下文，指导模型完成当前任务。

我设计Skill时，先定义触发条件和不适用边界，避免多个Skill职责重叠。再明确任务所需输入、前置条件、关键步骤、工具使用方式、异常处理和验收证据。核心流程放在`SKILL.md`，细节资料按需加载，稳定的检查动作交给脚本，从而减少上下文膨胀和模型临场猜测。

在治理上，我会把Skill当作代码处理：测试它该触发时是否触发、不该触发时是否被排除、关键流程是否正确、最终结果是否满足安全和验收要求；同时记录版本和trace，线上失败案例回流评测集。权限、参数校验和高风险确认不能只靠Skill约束，应由Harness、Server或工具权限层强制执行。



**Skill和Prompt有什么区别？**

Prompt是当前任务直接给模型的指令；Skill是可按需加载、可复用的任务包。Skill的核心内容会以Prompt或上下文影响模型，但它还包含触发条件、参考资料、脚本、模板和验收规则。



**Skill和RAG有什么区别？**

Skill主要解决“这类任务应该怎么做”，提供流程和经验；RAG主要解决“这次任务依据什么事实”，提供与当前问题相关的证据。实际系统中，Skill可以规定检索流程，RAG为该流程提供事实依据。



**为什么不把所有Skill都放进总Prompt？**

会导致上下文膨胀、成本上升、规则互相干扰，模型也更难判断当前任务真正该遵循哪套流程。因此通常先暴露名称和简短描述，命中后再加载完整Skill，资料和脚本再按需使用。



**Skill能保证模型不越权吗**

不能。Skill 只是上下文指导，模型可能不遵守。真正的权限、参数校验、限流、高风险确认和停止条件必须由 Harness、Server 或工具侧强制执行。
