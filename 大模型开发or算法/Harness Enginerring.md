###### 1.Harness Engineering

Harness是包在模型外面的运行时控制系统。

模型负责提出下一步建议，例如回答、调用工具、继续搜索或请求澄清；Harness不替模型思考，但负责决定这些建议能否执行、如何执行、执行结果如何回填，以及任务何时成功或必须停止。

用户目标——>Harness 组装上下文——>模型提出回答或Tool Call——>Harness 校验、授权、执行——>工具返回真实Observation——>Harness更新状态与预算——>模型继续决策——>Harness验收完成或强制停止

模型有三个根本限制：

- 它可能生成错误的工具名、参数或路径

- 它可能把工具失败误认为成功，或者反复走同一路径

- 它不能可靠地自己执行权限控制、预算控制和任务验收

因此，不能只靠Prompt写“请谨慎操作”“不要重复调用工具”等。

Prompt是软指导，Harness才能执行硬控制。

###### 2.Harness的六项核心职责

| 职责     | Harness任务                         |
| ------ | --------------------------------- |
| 上下文组装  | 放入当前目标、约束、相关记忆、工具描述和最近Observation |
| 状态管理   | 保存任务进度、工具结果、重试次数、未完成事项和检查点        |
| 工具执行   | 解析模型调用，校验Schema、权限和风险，再执行Tool     |
| 控制循环   | 发现重复、无进展、超时或预算超限，并决定重试、重规划、澄清或停止  |
| 测试与安全  | 用真实产物、测试结果和业务规则判断是否完成；高风险操作要求确认   |
| 可观测与评测 | 记录trace、成本、延迟、失败原因，并将线上问题回流评测集    |



- Agent：包含模型、Prompt、工具、记忆、规划和任务逻辑的整体应用。

- Harness：其中负责驱动和约束执行过程的运行时骨架

Harness+LLM=Agent

###### 3.Harness如何组装上下文

模型每次推理只能看到本轮请求中被放入上下文的内容。Harness的工作不是保存一份越来越长的聊天记录，而是每轮从状态、记忆、资料和工具结果中，挑选当前真正需要的信息重新组装。

| 层级   | 放什么                       | 目的              |
| ---- | ------------------------- | --------------- |
| 固定规则 | 系统边界、安全规则、输出要求            | 保证基本行为稳定        |
| 当前任务 | 用户目标、已确认约束、成功标准           | 让模型知道现在要完成什么    |
| 当前进展 | 已执行步骤、工具结果、失败原因、待办事项      | 防止重复和丢失进度       |
| 按需知识 | 匹配的Skill、RAG证据、相关长期记忆     | 补充流程与事实依据       |
| 可用能力 | 当前允许调用的Tool、参数Schema、权限状态 | 让模型知道能做什么、不能做什么 |



Harness 应优先保留结构化任务状态，而不是盲目保留全部原始过程。

**上下文组装的基本流程**

读取任务状态——>识别当前阶段与下一步决策需要什么——>选取相关Skill、记忆和RAG证据——>加入最近必要的工具Observation——>根据优先级压缩，控制Token预算——>发送给模型

当发生长度冲突时，通常按照下面的顺序保留（由上到下，优先级逐渐降低）

1.安全与系统规则

2.当前任务目标和已确认约束

3.当前任务的关键状态与真实Observation

4.与当前问题直接相关的证据

5.最近对话和补充背景

原则：越影响安全、正确性和下一步决策的信息，优先级越高。

###### 4.工具执行与状态更新

模型生成Tool Call只是一个执行建议，不是系统命令。Harness需要把这份建议经过校验、执行和记录，才允许它影响外部环境或任务状态。

模型提出Tool Call——>Harness校验——>必要时请求用户确认——>执行Tool——>规范化结果为Observation——>更新任务状态与检查点——>将必要Observation回填模型

| 校验层     | 要解决的问题                    |
| ------- | ------------------------- |
| 格式校验    | 工具名、必填参数、类型、枚举、数值范围是否正确   |
| 权限校验    | 当前用户和Agent是否有权执行该操作       |
| 业务前置条件  | 目标资源是否存在、当前状态是否允许操作       |
| 风险校验    | 是否涉及删除、发送、支付、生产环境修改等高风险动作 |
| 资源与预算校验 | 是否超出调用次数、时间、费用或并发限制       |

Tool 结果应变成结构化 Observation，Harness 不应把原始堆栈、密钥或冗长日志直接塞回模型，而应将结果整理为模型可行动的信息。

一个好的Observation至少告诉模型：

- 调用是否成功

- 得到了哪些事实、产物或状态变化

- 失败属于什么类型

- 是否可重试

- 下一步可采取什么行动



每次工具执行后，Harness 都应记录状态，而不是只把结果临时交给模型。



检查点是某个可恢复的任务快照，通常在关键状态变化后保存，例如：

- 准备执行高风险操作前

- Tool成功改变外部状态后

- 长任务完成一个阶段后

- 模型或工具服务异常前后

当进程中断、调用超时或需要人工接管时，系统可从检查点恢复，不必从头开始，也不会忘记已经完成的步骤。



###### 5.失败恢复与可靠性控制

Harness的恢复策略不是“报错就再跑一次”。

1.发现失败

2.判断失败类型

3.对可能修改外部状态的操作，确认结果是否未知

4.选择对应处理方式

5.记录本次处理

| 失败类型       | 典型例子              | 正确处理               |
| ---------- | ----------------- | ------------------ |
| 临时基础设施基础   | 网络超时、限流等          | 有限重试，使用退避策略        |
| 参数或格式错误    | 漏字段、路径错误、参数类型不对   | 返回具体错误，让模型修正后重新调用  |
| 权限或业务规则错误  | 无权限、资源不存在、状态不允许修改 | 不应原样重试，申请授权、换方案或停止 |
| 工具成功但任务未完成 | 测试运行成功，但测试仍未通过    | 回填结果，让模型重新规划下一步    |
| 结果未知的写操作   | 发起支付后超时，不确定是否已扣款  | 先查询真实状态，不能直接重复执行   |
