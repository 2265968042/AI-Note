### 1.Agent评估全景图

Agent 评测不是只看最终答案，而是沿着生命周期评估：开发前定标准，开发中测组件，上线前测完整链路，上线后看真实反馈。

- 开发前：
  
  - 定义成功标准。比如任务完成率、工具调用准确率、回答质量、延迟、成本和安全边界等等
  
  - 模型选型。比较不同模型在目标场景下的效果、成本、延迟和稳定性等

- 开发中：
  
  - 对agent的关键组件分别进行测评。包括 Prompt、RAG 检索质量、工具选择、参数生成、规划能力、多轮对话状态管理等。
  
  - 同时观察中间轨迹是否合理，比如是否选对工具、参数是否正确、是否能根据工具结果继续规划

- 上线前：
  
  - 做端到端测评。验证完整任务链路是否稳定完成。
  
  - 进行小规模用户测试、仿真测试、安全测试等，并建立自动化评测pipeline

- 上线后：
  
  - 基于真实流量持续监控，包括任务成功率、失败率、工具调用错误率等等。
  
  - 发现问题后回流到测试集和评测 pipeline 中，持续迭代。

### 2.评测细节

###### 2.1 LLM-as-a-judge

- `LLM-as-a-judge` 是什么？
  - 是一个（通常更强的）大模型，按照预先写好的评分标准`rubric`，去给另一个Agent的输出打分或排序。它是目前最主流的自动评估手段。
- 为什么 Agent 评测需要它？
  - Agent的输出大多是开放式自然语言，没有唯一的标准答案，没有办法像传统评测那样进行精确匹配。LLM能像人一样理解语义，又能像程序一样批量自动化跑。
- 它有哪三种典型用法？
  - 单点打分：给一个输出打一个绝对分
  - 对参考打分：把输出和“标准答案”相比，判断是否一致，进行打分。
  - 两两比较：给出A、B两个输出，让裁判选择哪个更好。
- 它有什么缺点或风险？
  - 自我偏好：裁判偏向自己生成的答案。
  - 首位偏差：两两比较时偏向排在前面的那个。
  - 冗长偏差：偏向更长的回答，哪怕没更好。

看不到裁判模型和它的提示词，就不要相信它给的分数。

不同 judge 模型、prompt、rubric 的分数不可直接横向比较

###### 2.2 比较式评估

**是什么：** 不给某个结果打绝对分数，而是针对同一个问题，将不同的Agent或者模型的输出两两比较，由人或LLM Judge 选出更好的一个；收集大量胜负结果后，进一步形成模型排名。

**为什么测：** 很多开放式回答很难准确打绝对分数，但比较两个答案哪个更好通常更容易，更加稳定。所以适合评估和排序多个Agent或模型

**怎么测：** 

针对同一批问题，分别生成多个Agent回答

让人工评委或者LLM Judge对两个回答进行投票

最后根据胜负记录，用 Elo 或 Bradley-Terry 等方法计算整体排名。

**和 A/B 测试有什么区别：** 

A/B 测试通常是线上的：将不同版本分给不同用户群，比较真实业务指标，例如留存、转化、满意度和投诉率。

比较式评估通常是离线的：同一个问题的多个输出交给同一个评委比较。

**风险是什么：** 

偏好不等于正确。评委可能更喜欢语气讨好、篇幅更长但实际错误的回答。
因此需要专业评委，并注意首位偏差、冗长偏差等问题。

**补充：**

有些任务能用程序直接判断对错，就不要优先让大模型当裁判。比如让 Agent 写 SQL：SQL 能否执行、结果是否正确，可以直接验证；这比让另一个 LLM 主观打分更客观、更便宜，也更容易复现。

1.功能正确性：有标准答案，或能实际执行验证。

2.相似度。有参考答案，但允许措辞不同，例如翻译、摘要。

3.困惑度。衡量模型对文本的“意外程度”，可辅助判断语言流畅性或发现测试数据污染；

能用功能正确性就不用相似度，能用相似度就不优先用LLM as a judge

越靠前就越客观、便宜和可复现。

### 3.选型期：选基模

选模型不是“榜单第一就选谁”，而是“业务场景需要什么能力，就选能满足这些能力、成本和约束的模型”，最后再用私有测试集进行验证。

场景->能力需求->候选模型->私有测试验证->最终选择

- 为什么不能只按模型排行榜选基模？
  - 公开榜单可能存在数据污染，导致排名虚高
  - 榜单任务和我们的任务未必相关
  - 闭源模型涉及成本和数据隐私
- 选基模时，除了回答质量，还要考虑哪些因素？
  - 硬性约束：成本上限、延迟上限、是否支持私有部署、上下文长度
  - 软指标：回答质量和能力
  - 是否贴合应用场景
  - 是要自建开源模型还是要调用API
  - 最终必须用真实业务数据构建私有测试集验证。
- 如果 Agent 必须调用外部工具，模型最关键的能力是什么？
  - function calling能力，包括能否选对工具、稳定生成正确参数，同时还需要稳定的结构化输出和指令遵循能力。

**如何用“硬约束先筛选、软指标再比较、私有测试集最终验证”的方式完成选型。**

```
第一步：硬约束筛掉不合格模型（成本、延迟、私有化部署、上下文长度和工具调用支持）
第二步：从剩余模型里挑几个候选
第三步：用自己的真实任务测试，选最合适的（比较任务成功率、工具调用准确率、成本和延迟）
```

### 4.上线前-组件测评

Agent是由Prompt、RAG、工具、规划等组件组成的。上线前不能只看最终结果，要把每个组件拆开测，先定位哪个零件有问题。

###### 4.1 Prompt评测

Prompt评测就是评估提示词写得好不好、稳不稳定和安不安全。

1. 为什么 Prompt 不能只靠感觉判断好不好？
   
   - Prompt对agent的行为很敏感，少量措辞变化都可能影响输出质量、工具调用和安全性。因此要在同一批测试问题上进行批量比较。

2. Prompt 评测主要测哪三方面？
   
   - 好不好用。质量评测。
   
   - 能不能自动调优。自动prompt优化工具，不是测评Prompt能不能自动调优，而是借用工具自动搜索或者改进Prompt。
   
   - 抗不抗攻击。防御性评测。能否抵抗提示注入、越狱等攻击。

3. 如何比较两个 Prompt 哪个更好？
   
   - 同一批测试问题分别运行两个Prompt，再用功能正确性、相似度或者LLM-as-a-judge评分。最后汇总成功率、平均分、工具调用准确率和失败案例等，选择综合表现更好的版本。

###### 4.2 RAG/检索评测

RAG是“先检索、再生成”，所以评测也必须拆成检索阶段和生成阶段，不能只看最终回答。

我觉得应该有三个指标，分别是答案相关性、忠实度、上下文相关性。

具体来讲，**忠实度**是指LLM judeg判断LLM的输出是否是根据召回文本的内容生成的。

**答案相关性**是衡量生成的答案是否和用户的问题相关的。

**上下文相关性**是用于判断召回文本是否和用户问题相关的。

具体来讲：

**忠实度**的计算方式通常包括两个步骤：

1.使用LLM生成的问题和答案，让大模型生成多个陈述。

2.让LLM**判断**是否可以通过召回的文本，推断出这些陈述。最后\frac{采用能够推断出来的陈述}{总陈述量}作为忠诚度的评分。

**答案相关性**：根据LLM的回答生成若干个假问题，然后计算假问题和真问题的相似度，将相似度平均值作为答案相关性的评分。

**上下文相关性**：让LLM挑选出召回文本片段中能够回答用户问题的文本子集，用文本子集占召回文本的比例作为上下文的相关性数值。

还需要再补充两个检索阶段的指标：

context precision:找回来的内容里，有多少真的相关。

context recall:应该找回的相关内容，实际找回了多少。

###### 4.3工具调用评测

工具调用评测，就是检查Agent调用API、函数或数据库时，工具有没有选对、参数有没有填对、调用顺序有没有合理。

1. 工具调用评测的三层分别是什么？
   1. 能力层。Agent 能否在多个工具中选对工具并生成正确参数。
   2. 行为层。调用工具的顺序对不对。
   3. 代码层。工具函数本身写的对不对。
2. 工具调用时主要检查哪四项？
   1. 函数名对不对
   2. 必填参数是否填齐
   3. 有没有瞎编参数
   4. 参数值是否正确
3. 为什么要加入“不该调用工具”的测试样本？
   1. 知道何时不该用工具和知道何时改用工具一样重要。避免工具幻觉。

###### 4.4 规划/推理评测

工具调用评测：看某一次调用对不对。例如工具名、参数值对不对。

规划/推理评测：看整个任务的决策路径对不对。

1. 规划 / 推理评测和工具调用评测有什么区别？
   1. 工具调用评测：看某一次调用对不对。例如工具名、参数值对不对。
   2. 规划/推理评测：看整个任务的决策路径对不对。
2. 规划评测最常见的三类失败是什么？
   1. 该不该用这个工具。在决策层面选错了工具或者多走了无谓的一步。选择哪个工具属于规划评测，参数填没填对属于工具调用评测。
   2. 目标失败。没达成目标或者违反了约束。
   3. 反思错误。没有完成任务，agent却认为完成了。
3. 如何评测一个 Agent 的规划是否合理？
   1. 给Agent一个需要分几步才能完成的任务，提前定义理想步骤链和必须满足的约束。
   2. 运行Agent并记录实现轨迹，再对比是否漏步骤、违反约束或自以为完成；
   3. 最后统计这些失败类型和成功率。

### 5.上线前：集成/系统评测

零件合格，不等于整机合格。

给Agent一个完整任务->让它端到端运行->看任务是否真正完成，以及过程中是否可靠。

###### 5.1 任务结果评测

最终有没有完成用户任务。

1. 为什么组件评测都通过后，仍然需要系统评测？
   
   1. 零件合格，不等于整机合格。

2. 任务结果评测主要在判断什么？
   
   1. 给Agent一个完整任务，它最终做成了没有。

3. 任务有没有完成的评估方法。
   
   对端到端任务，我会按目的选择指标。模型选型或排名时，用 Pass @k 区分是否具备成功能力；对稳定性要求高的关键任务，用 Pass^k 看多次运行能否全部成功；开发诊断时，用 rubric 拆分时间、约束、工具调用等维度定位问题；上线监控时，用相似度或忠实度这类连续指标识别质量漂移。
   
   Pass@k：同一任务运行 k 次，至少成功一次；
   Pass^k：同一任务运行 k 次，每一次都成功。

###### 5.2 轨迹评测

Agent最终答案看起来对，不代表它的执行过程就是对的。

1. 为什么最终结果正确，仍要做轨迹评测？
   1. agent不能只看结果，还要看agent走到终点的整条路径。它依次做了哪些动作、调了哪些工具、顺序对不对。最终结果可能是碰巧正确，但中间有无用调用、错误顺序、高成本，甚至先执行高风险动作后确认，因此上线后不可靠。
2. 什么是 Agent 的轨迹？
   1. agent从输入到输出的整条路径。它依次做了哪些动作、调了哪些工具、顺序对不对。搜索->筛选—>下单->确认
3. 精确匹配、按序匹配、任意顺序匹配有什么区别？
   1. 精确匹配：动作序列和标准轨迹完全一致。
   2. 按序匹配：关键动作按正确顺序出现即可，允许中间有别的。

###### 5.3 多轮交互评测

单轮问答测的是“这一句答得对不对”，多轮交互测的是“用户不断补充、追问和改主意时，Agent最后还能不能完成任务”

1. 为什么不能只用固定的一问一答来评测多轮 Agent？
   1. 真实用户不会一次把需求说全。前面的组件评测、单轮评测都假设“一问一答”，但实际场景是“边聊边改”。如果不专门测多轮，上线后才会Agent一到真实对话就乱套。
2. 多轮交互评测的任务包包含哪三类信息？
   1. 环境/后台状态：例如菜单、库存、价格、配送时段。被测 Agent、用户模拟器、判分器都能看到这部分信息。
   2. 隐藏用户目标卡：它规定用户真正要完成什么，以及可能在什么时候改变条件；只有用户模拟器能看到。
   3. 评分Rubric:只给判分器、作用是规定最后怎么判Pass/Fail
3. 多轮交互结束后，主要根据什么判断成功或失败？
   1. 结构化终态用代码判断
   2. 语义行为用LLM judge判断
   3. 两者共同依据 rubric 判定 Pass / Fail。

此外，同一任务可以多次运行，用 `Pass^4` 检验面对不同对话路径时是否仍然稳定完成。

###### 5.4 多Agent协作评测

它不只问任务做成了吗？还要问“多个Agent有没有正确分工、正确交接，而且每个Agent的加入是否真的有价值”

1. 多 Agent 协作评测相比单 Agent 评测，多了哪些风险？
   1. 他们之间会不会协作、有没有选对该干活的agent、加agent到底是帮忙还是添乱。
   2. 交接时有没有丢失关键信息、交接顺序正确还是错误、重复工作和状态冲突。
2. 什么是消融评测？它解决什么问题？
   1. 消融评测不是随机去掉一个 Agent，而是**有控制地一次去掉一个指定 Agent**，并在同一批测试任务上比较。
   2. 通过成功率、成本等，可以判断某个Agent是不是必要的。
3. 多 Agent 系统为什么要记录 trace？
   1. 因为它能记录每个 Agent 的输入、输出、交接对象、耗时、token 和调用次数。
   2. 通过trace可以发现是否选错Agent、是否丢失关键信息、是否重复推理、是否存在无效交接或者状态冲突。
   3. 并且等定位具体问题发生的位置。

多 Agent 协作评测要看交接链是否正确、每个 Agent 是否有边际收益，以及协作过程是否健康可追踪。
